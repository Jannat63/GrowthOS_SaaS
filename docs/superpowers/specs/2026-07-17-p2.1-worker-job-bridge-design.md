# P2.1 — Worker & Data Plumbing — Design Spec

**Date:** 2026-07-17
**Milestone/Phase:** M2 · P2.1
**Status:** Approved design — ready for implementation plan
**Depends on:** P1.1 (packages/db), P1.3 (Fastify domain skeleton)

## Goal

Stand up the async worker and the data plumbing every M2 feature relies on: a Python worker,
the enqueue → process → status job pattern, the `background_jobs` table, seeded ClickHouse, and
seeded `platform_connections`. This phase has **no user-facing feature UI** — it is the pipe that
later slices (P2.2+) push real work through.

## Locked decisions (from brainstorming)

1. **Plain Python worker, not Celery.** A small worker that pops a job off Redis, runs a handler,
   writes the result to Postgres. Celery's value (retries, beat scheduling, concurrency, Flower) is
   not needed on M2's seeded, on-demand jobs. The job **handlers** are designed as plain functions so a
   later swap to Celery (M3, when live external APIs need retries/scheduling) is a contained change to
   the ~consumer loop only. This consciously defers the "Celery worker" named in CLAUDE.md, with a clear
   upgrade path.
2. **Redis stays as the mailbox (transport), Postgres is the source of truth (state).** Redis is the
   pickup channel between Node and Python; `background_jobs` in Neon holds authoritative job state.
   Local Redis via Docker in dev (`redis://localhost:6379`); Upstash cloud deferred to production.
3. **Polling now, WebSocket deferred to P2.7.** Clients poll `GET /workspaces/:id/jobs/:jobId`. The
   `job:complete` WebSocket push belongs to the P2.7 notification center. YAGNI here.
4. **Tooling:** built-in `venv` + `pip` + `requirements.txt` (matches legacy; no new tools). Worker
   talks to Neon via `asyncpg` and Redis via `redis-py`. Health endpoint via FastAPI.

## The job-bridge contract

Postgres is authoritative for state; Redis is the notification/pickup channel.

Enqueue (Fastify):
1. Insert a `background_jobs` row with `status='queued'` → obtain `jobId` (UUID).
2. `LPUSH jobs:queue <envelope>` where the envelope is:
   ```json
   { "v": 1, "jobId": "uuid", "workspaceId": "uuid", "type": "echo", "payload": { } }
   ```
3. Respond `202 { "jobId": "uuid", "statusUrl": "/api/v1/workspaces/:id/jobs/:jobId" }`.

Because the DB row is written **before** the Redis push, a worker crash never loses a job — the row
remains `queued` and can be re-driven. No Redis Streams/acks needed at this stage.

Consume (worker):
1. `BLPOP jobs:queue` (blocking) → parse + validate envelope (Pydantic).
2. Mark row `processing`, set `started_at`.
3. Look up handler by `type`; run it with `payload`.
4. On success: write `result` (JSONB), mark `complete`, set `completed_at`.
5. On failure: write `error` text, mark `failed`, set `completed_at`. Loop continues.

## background_jobs table (Drizzle, Neon)

Mirrors `docs/blueprint/DATA_MODELS.md`:

| column | type | notes |
|--------|------|-------|
| id | uuid pk default gen_random_uuid() | jobId |
| workspace_id | uuid → workspaces(id) | tenancy |
| type | text not null | handler key, e.g. `echo` |
| status | text default 'queued' | queued \| processing \| complete \| failed |
| progress | smallint default 0 | 0–100 (optional use in P2.1) |
| result | jsonb | handler output |
| error | text | failure message |
| queued_at | timestamptz default now() | |
| started_at | timestamptz | |
| completed_at | timestamptz | |

(The blueprint's `celery_task_id` column is omitted — no Celery. Can be re-added in M3 if adopted.)

## Component layout

```
apps/worker/                    # NEW — Python 3.12
  app/
    main.py          # FastAPI app: GET /health + startup launches the consumer task
    consumer.py      # BLPOP loop: pop → validate → dispatch → update row
    dispatch.py      # handler registry {type -> async handler}
    handlers/
      echo.py        # first handler (dummy job)
    jobs.py          # background_jobs read/write via asyncpg
    envelope.py      # Pydantic model for the job envelope
    config.py        # env: REDIS_URL, DATABASE_URL, QUEUE_KEY
  seeds/
    clickhouse_seed.py        # insert fixture ad_performance rows
    platform_connections_seed.py  # insert stub connection rows into Neon
  tests/
    test_dispatch.py
    test_echo_handler.py
    test_consumer_integration.py
  requirements.txt   # redis, fastapi, uvicorn, asyncpg, pydantic, clickhouse-connect
  .env               # gitignored (REDIS_URL, DATABASE_URL)
  .env.example
  README.md

apps/api/src/
  jobs.ts            # enqueue(type, workspaceId, payload) helper + GET /jobs/:jobId route
  routes/v1.ts       # register the jobs route

packages/db/
  src/schema/jobs.ts # background_jobs table
  drizzle/           # generated migration
```

The worker runs the consumer as an asyncio background task started on FastAPI startup, so one process
serves `/health` and drains the queue. `redis.asyncio` + `asyncpg` keep it fully async.

## Data flow (end to end)

```
Client        Fastify (apps/api)                 Redis            Worker (apps/worker)        Neon
  |  POST .../jobs (or a feature route)  |                          |                          |
  |------------------------------------> | INSERT background_jobs (queued) --------------------> |
  |                                      | LPUSH jobs:queue ------> |                          |
  |  <-- 202 {jobId, statusUrl} ---------|                          |                          |
  |                                      |                          | BLPOP jobs:queue          |
  |                                      |                          | UPDATE row -> processing->|
  |                                      |                          | run handler(payload)      |
  |                                      |                          | UPDATE row -> complete -->|
  |  GET .../jobs/:jobId --------------->| SELECT background_jobs ------------------------------>|
  |  <-- 200 {status, progress, result}--|                          |                          |
```

## Error handling

- Handler raises → row `failed` with the message; loop keeps running (one bad job never kills worker).
- Unknown `type` → `failed` with "no handler registered for '<type>'".
- Malformed envelope → logged + skipped (dropped from queue); DB row, if any, marked `failed`.
- Redis/DB connection loss → reconnect with exponential backoff.
- `GET /jobs/:jobId` → `requireWorkspaceMember` guard; job outside caller's workspace →
  `WORKSPACE_NOT_FOUND` (don't leak existence). Standard error envelope `{ error: { code, message, statusCode } }`.

Worker (pytest):
- Unit — each handler as a plain function (`echo` returns its payload).
- Unit — dispatcher resolves known types, raises for unknown.
