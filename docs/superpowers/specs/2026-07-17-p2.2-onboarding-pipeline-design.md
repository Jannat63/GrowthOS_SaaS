# P2.2 — Onboarding Pipeline — Design Spec

**Date:** 2026-07-17
**Milestone/Phase:** M2 · P2.2
**Status:** Approved design (Option B) — ready for implementation plan
**Depends on:** P2.1 (worker + job pipeline), P1.2 (Better Auth workspaces), P1.4a (onboarding UI)

## Goal

Wire the existing (client-only) onboarding wizard to a real backend pipeline: persist the user's
business profile, then run a worker job that (stub-)crawls the site and generates a channel-mix +
90-day **strategy**, surfaced to the user on a review step before landing on the dashboard. This is
the **first real use of the P2.1 job pipeline** (the `echo` placeholder → a real `onboarding_analyze`
handler).

## Locked decisions

1. **Seeded stub crawler.** The crawl handler returns fixture pages/keywords — no real HTTP fetch.
   The pipeline, statuses, progress, and UI states are all real; only the crawl *data* is seeded.
   Real crawl (port `legacy/services/seo-service/app/crawler.py`) is deferred to **M3**.
2. **Recommendations are OUT of P2.2 (Option B).** Rationale: introducing a second recommendation
   producer (Python templates) alongside the canonical tested TS cross-channel engine would create
   two sources of truth for the product's core object, built in P2.2 only to be reconciled/removed in
   P2.3. The `recommendations` table + `/recommendations` endpoint + unifying the frontend
   `Recommendation` shape are **deferred to P2.3**, where the first *real* engine drives the contract.
   The dashboard keeps its existing mock-backed recommendation queue one more slice.
3. **`workspaces` is the single source of truth for the onboarding profile + gate.** `websiteUrl`,
   `businessCategory`, `monthlyAdBudget`, `onboardingStep`, `onboardingComplete` **already exist** on
   `workspaces` (Better Auth `additionalFields`). We use them; we do **not** duplicate them into a new
   table. `onboardingComplete` is the boolean gate; `onboardingStep` is granular UI progress.
4. **Generated artifacts get their own domain table.** Crawl summary + strategy are system-generated
   (not user identity), so they live in a new `onboarding_analyses` table keyed by `workspace_id`
   (app-layer, per the `tenancy.ts` pattern) — keeping the Better-Auth `workspaces` row clean.
5. **Deterministic strategy (D4).** Channel-mix + 90-day plan come from category templates; Claude is
   deferred behind a flag.

## Scope

In scope:
- Persist profile via a real `POST /workspaces/:id/onboarding` (updates existing `workspaces` columns).
- `onboarding_analyses` table (crawl summary + strategy jsonb).
- `onboarding_analyze` worker job: stub-crawl → strategy → persist → progress updates.
- `mark_progress()` added to the worker jobs repo.
- Wizard wired to real submit + job-status polling (loading / error / **review** states) rendering the
  generated strategy, then a completion step that flips `onboardingComplete`.
- Idempotency: a second submit while a job is in flight returns the existing job, not a duplicate.

Out of scope (deferred):
- `recommendations` table + endpoint + frontend `Recommendation` unification → **P2.3**.
- Real crawl, real OAuth, pixel/tag validators → **M3**.

## Data model

**Reuse (already on `workspaces` — no change):** `websiteUrl`, `businessCategory`,
`monthlyAdBudget`, `onboardingStep`, `onboardingComplete`.

**New — `onboarding_analyses`** (Drizzle, `packages/db/src/schema/onboarding.ts`):

| column | type | notes |
|--------|------|-------|
| id | uuid pk default gen_random_uuid() | |
| workspaceId | text not null, unique | app-layer key → workspaces.id (1:1) |
| crawlSummary | jsonb | stub crawl output (pages, topKeywords, issues) |
| strategy | jsonb | channel-mix + 90-day plan (shape below) |
| generatedAt | timestamptz default now() | |
| createdAt / updatedAt | timestamptz default now() | |

Unique on `workspaceId` → upsert makes re-analysis idempotent (overwrites, no dupes).

### `strategy` jsonb shape (defined, so the review UI can render it)

```jsonc
{
  "summary": "string — 1-2 sentence overview",
  "channelMix": [
    { "channel": "seo" | "google_ads" | "meta_ads", "allocationPct": 40, "rationale": "string" }
  ],                                        // allocations sum to 100
  "ninetyDayPlan": [
    { "phase": "Weeks 1-4: Foundation", "focus": "string", "milestones": ["string", "..."] }
  ]
}
```

### `crawlSummary` jsonb shape

```jsonc
{ "pagesCrawled": 12, "topKeywords": ["string"], "issues": ["string"], "seeded": true }
```

## API (apps/api)

All under `/api/v1`, camelCase, guarded by `requireWorkspaceMember`.

- **`POST /workspaces/:id/onboarding`** (min role `admin`; the onboarding user is `owner`).
  Body (zod): `{ websiteUrl: string(url), businessCategory: string, monthlyAdBudget: number>=0 }`.
  1. Update `workspaces` row (Drizzle) with the profile fields + `onboardingStep='analyzing'`.
  2. **Idempotency guard:** if a `background_jobs` row exists for this workspace with
     `type='onboarding_analyze'` and `status IN ('queued','processing')`, return that existing
     `{ jobId, statusUrl }` (202) instead of enqueuing a second.
  3. Else `enqueue({ workspaceId, type: 'onboarding_analyze', payload: { websiteUrl, businessCategory, monthlyAdBudget } })`.
  Returns `202 { jobId, statusUrl }`.

- **`GET /workspaces/:id/onboarding`** (min role `viewer`). Returns
  `{ profile: { websiteUrl, businessCategory, monthlyAdBudget, onboardingStep, onboardingComplete }, analysis: { crawlSummary, strategy } | null }`
  — the review step reads the strategy here after the job completes.

- **`POST /workspaces/:id/onboarding/complete`** (min role `admin`). Sets
  `onboardingComplete=true`, `onboardingStep='complete'`. The single completion gate.

Job status polling reuses the existing **`GET /workspaces/:id/jobs/:jobId`** from P2.1.

## Worker (apps/worker)

New handler `onboarding_analyze` registered in the P2.1 dispatch registry.

- **`app/handlers/onboarding.py`** — `handle(payload)`:
  1. `crawl = stub_crawl(payload["websiteUrl"])` → `mark_progress(pool, job_id, 40)`
  2. `strategy = generate_strategy(payload["businessCategory"], payload["monthlyAdBudget"])` →
     `mark_progress(pool, job_id, 80)`
  3. `upsert_onboarding_analysis(pool, workspace_id, crawl, strategy)` +
     set `workspaces.onboarding_step='review'` → returns `{ "strategySummary": strategy["summary"], "pagesCrawled": crawl["pagesCrawled"] }` (job result)
- **`app/fixtures/crawl.py`** — `stub_crawl(url) -> dict` (deterministic fixture crawl summary).
- **`app/strategy.py`** — `generate_strategy(category, budget) -> dict`. Category→template map for
  `ecommerce | saas | local_services | content | other` (default `other`); channel-mix weights
  adjusted by budget band. Pure + deterministic (D4).
- **`app/jobs.py`** — add `mark_progress(pool, job_id, progress: int)` and
  `upsert_onboarding_analysis(pool, workspace_id, crawl, strategy)`.

The handler must not raise on a known-bad category (falls back to `other`); unknown job errors are
handled by the P2.1 consumer (`mark_failed`).

## Frontend (apps/web)

Reuse the existing `app/(auth)` pages + Zustand `onboarding` store; add real backend calls.

- **business-info / connect-accounts** — unchanged collection UI; the final submit now calls
  `POST /workspaces/:id/onboarding` (via a `lib/hooks/useOnboarding*` mutation) instead of only
  `router.push`.
- **New "analyzing" state** — polls `GET /jobs/:jobId` (reusing a `useJob(jobId)` hook), showing
  progress; on `failed` shows an error + retry; on `complete` advances to review.
- **New "review" step** — fetches `GET /workspaces/:id/onboarding`, renders the `strategy`
  (channel-mix + 90-day plan) on shadcn primitives; a "Looks good" button calls
  `POST /workspaces/:id/onboarding/complete` then routes to the dashboard.
- Dashboard recommendation queue is unchanged (still mock-backed — recs land in P2.3).

No new component library; shadcn primitives from `packages/ui`.

## Error handling

- Invalid onboarding body → `VALIDATION_ERROR` (400).
- Non-member / cross-workspace → `FORBIDDEN` / `WORKSPACE_NOT_FOUND` per the P2.1 guard pattern.
- Job failure → row `failed`; the analyzing UI surfaces the error + offers retry (re-POST onboarding).
- Worker: bad category → `other` template (no raise); DB/Redis loss → P2.1 reconnect/backoff.

## Testing (TDD)

- **Worker (pytest):** `stub_crawl` (deterministic), `generate_strategy` per category + budget band
  (allocations sum to 100, plan non-empty), `upsert_onboarding_analysis` idempotency (2nd call
  overwrites, still one row), `onboarding_analyze` integration (push job → `onboarding_analyses` row
  has strategy + `onboarding_step='review'` + job `complete`).
- **API (vitest):** `POST /onboarding` updates profile + enqueues (and the in-flight idempotency guard
  returns the same jobId); `GET /onboarding` returns profile + analysis; `POST /complete` flips the
  gate.
- **E2E (data layer):** submit onboarding → worker runs → `GET /onboarding` returns a strategy;
  `onboardingComplete` flips after `/complete`. (Authed HTTP path needs a session cookie, per P2.1.)

## Reuse

- P2.1 job pipeline (`enqueue`, `background_jobs`, consumer, dispatch) — extended with one handler.
- Existing onboarding pages + `lib/stores/onboarding.ts` + `OnboardingShell`.
- `legacy/services/seo-service/app/crawler.py` — reference only (real crawl is M3).
